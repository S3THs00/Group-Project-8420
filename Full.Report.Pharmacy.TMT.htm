Threat Model Name: OpenEMR External Pharmacy Prescription Exchange

Owner: Erik Osmera

Reviewer:

Contributors: Team 4

Description: Level 1 DFD threat model of prescription and refill transactions between an external pharmacy/ePrescribing service and OpenEMR.

Assumptions: External prescription traffic uses HTTPS/TLS. OpenEMR uses its documented authentication, authorization, auditing, and secure database practices where configured.

External Dependencies: External pharmacy/ePrescribing service, network/TLS infrastructure, database platform

Interaction: Authenticated Prescription Transaction

1. OpenEMR Web Interface Process Memory Tampered  [State: Not Applicable]  [Priority: High] 

Category:Tampering
Description:If OpemEMR Web Interface is given access to memory, such as shared memory or pointers, or is given the ability to control what OpenEMR Prescription Processing Service executes (for example, passing back a function pointer.), then OpemEMR Web Interface can tamper with OpenEMR Prescription Processing Service. Consider if the function could work with less access to memory, such as passing data rather than pointers. Copy in data provided, and then validate it.
Justification:The Web Interface and Prescription Processing Service exchange application data and do not share pointers, executable references, or shared process memory in this Level 1 model.

2. Elevation Using Impersonation  [State: Not Applicable]  [Priority: High] 

Category:Elevation Of Privilege
Description:OpenEMR Prescription Processing Service may be able to impersonate the context of OpemEMR Web Interface in order to gain additional privilege.
Justification:The Prescription Processing Service does not elevate privileges by impersonating the Web Interface&#39;s operating-system identity. Application authorization is handled separately.

Interaction: HTTPS: Prescription Refill Request

3. Spoofing the External Pharmacy/ePrescribing Service External Entity  [State: Needs Investigation]  [Priority: High] 

Category:Spoofing
Description:External Pharmacy/ePrescribing Service may be spoofed by an attacker and this may lead to unauthorized access to OpenEMR Web Interface. Consider using a standard authentication mechanism to identify the external entity.
Justification:OpenEMR supports authentication mechanisms, but the team&#39;s prior analysis found pharmacy-specific authentication only partially supported. The external pharmacy identity and authorization mechanism must be verified for this prescription workflow.

4. Cross Site Scripting  [State: Mitigation Implemented]  [Priority: High] 

Category:Tampering
Description:The web server 'OpemEMR Web Interface' could be a subject to a cross-site scripting attack because it does not sanitize untrusted input.
Justification:OpenEMR provides secure coding guidance requiring output encoding of user-controlled data. Externally supplied prescription data should be encoded before rendering to prevent stored or reflected XSS.

5. Elevation Using Impersonation  [State: Not Applicable]  [Priority: High] 

Category:Elevation Of Privilege
Description:OpemEMR Web Interface may be able to impersonate the context of External Pharmacy/ePrescribing Service in order to gain additional privilege.
Justification:The modeled OpenEMR Web Interface does not rely on operating-system process impersonation of the external pharmacy&#39;s security context. Authorization occurs at the application/API layer.

6. Potential Data Repudiation by OpemEMR Web Interface  [State: Needs Investigation]  [Priority: High] 

Category:Repudiation
Description:OpemEMR Web Interface claims that it did not receive data from a source outside the trust boundary. Consider using logging or auditing to record the source, time, and summary of the received data.
Justification:OpenEMR supports audit logging, but it should be verified that external prescription/refill transactions record source identity, timestamp, affected record, transaction ID, and result.

7. Potential Process Crash or Stop for OpemEMR Web Interface  [State: Needs Investigation]  [Priority: High] 

Category:Denial Of Service
Description:OpemEMR Web Interface crashes, halts, stops or runs slowly; in all cases violating an availability metric.
Justification:Malformed or excessive external requests could affect application availability. Request limits, exception handling, monitoring, and availability protections should be reviewed.

8. Data Flow HTTPS: Prescription Refill Request Is Potentially Interrupted  [State: Needs Investigation]  [Priority: High] 

Category:Denial Of Service
Description:An external agent interrupts data flowing across a trust boundary in either direction.
Justification:Interrupted prescription transactions should fail safely and record transaction status. Retry behavior, timeout handling, and failure logging require verification.

9. OpemEMR Web Interface May be Subject to Elevation of Privilege Using Remote Code Execution  [State: Needs Investigation]  [Priority: High] 

Category:Elevation Of Privilege
Description:External Pharmacy/ePrescribing Service may be able to remotely execute code for OpemEMR Web Interface.
Justification:Untrusted external data must not reach unsafe execution paths. Input validation, current security patches, dependency management, and least-privilege execution should be verified.

10. Elevation by Changing the Execution Flow in OpemEMR Web Interface  [State: Needs Investigation]  [Priority: High] 

Category:Elevation Of Privilege
Description:An attacker may pass data into OpemEMR Web Interface in order to change the flow of program execution within OpemEMR Web Interface to the attacker's choosing.
Justification:Externally supplied prescription data should be validated and processed using secure coding controls. The implementation should be reviewed for unsafe control-flow or injection paths.

Interaction: HTTPS: Prescription Refill Response

11. External Entity External Pharmacy/ePrescribing Service Potentially Denies Receiving Data  [State: Needs Investigation]  [Priority: High] 

Category:Repudiation
Description:External Pharmacy/ePrescribing Service claims that it did not receive data from a process on the other side of the trust boundary. Consider using logging or auditing to record the source, time, and summary of the received data.
Justification:Outbound prescription responses should be logged with destination, timestamp, transaction identifier, outcome, and acknowledgement where available. This should be verified in the workflow.

12. Spoofing of the External Pharmacy/ePrescribing Service External Destination Entity  [State: Needs Investigation]  [Priority: High] 

Category:Spoofing
Description:External Pharmacy/ePrescribing Service may be spoofed by an attacker and this may lead to data being sent to the attacker's target instead of External Pharmacy/ePrescribing Service. Consider using a standard authentication mechanism to identify the external entity.
Justification:OpenEMR should validate the destination pharmacy service using trusted endpoint configuration and TLS certificate validation. The exact validation behavior requires verification.

13. Data Flow HTTPS: Prescription Refill Response Is Potentially Interrupted  [State: Needs Investigation]  [Priority: High] 

Category:Denial Of Service
Description:An external agent interrupts data flowing across a trust boundary in either direction.
Justification:Failed or interrupted responses should be detected and logged, and the system should not treat an incomplete transaction as successful. Error and retry behavior require verification.

Interaction: Prescription Audit Event

14. Spoofing of Destination Data Store OpenEMR Audit Log DB  [State: Needs Investigation]  [Priority: High] 

Category:Spoofing
Description:OpenEMR Audit Log DB may be spoofed by an attacker and this may lead to data being written to the attacker's target instead of OpenEMR Audit Log DB. Consider using a standard authentication mechanism to identify the destination data store.
Justification:Audit database access should be authenticated and limited to authorized OpenEMR components. The deployment-specific database access controls require verification.

15. Potential SQL Injection Vulnerability for OpenEMR Audit Log DB  [State: Needs Investigation]  [Priority: High] 

Category:Tampering
Description:SQL injection is an attack in which malicious code is inserted into strings that are later passed to an instance of SQL Server for parsing and execution. Any procedure that constructs SQL statements should be reviewed for injection vulnerabilities because SQL Server will execute all syntactically valid queries that it receives. Even parameterized data can be manipulated by a skilled and determined attacker.
Justification:Audit entries may contain values derived from external transactions. Parameterized inserts should be used, but the audit-writing implementation should be verified.

16. Potential Excessive Resource Consumption for OpenEMR Prescription Processing Service or OpenEMR Audit Log DB  [State: Needs Investigation]  [Priority: High] 

Category:Denial Of Service
Description:Does OpenEMR Prescription Processing Service or OpenEMR Audit Log DB take explicit steps to control resource consumption? Resource consumption attacks can be hard to deal with, and there are times that it makes sense to let the OS do the job. Be careful that your resource requests don't deadlock, and that they do timeout.
Justification:High-volume or malicious requests could generate excessive audit activity. Storage limits, request throttling, and monitoring should be verified.

Interaction: Prescription Record Data

17. Weak Access Control for a Resource  [State: Needs Investigation]  [Priority: High] 

Category:Information Disclosure
Description:Improper data protection of OpenEMR Patient and Prescription DB can allow an attacker to read information not intended for disclosure. Review authorization settings.
Justification:OpenEMR supports RBAC/ACL controls, but enforcement must be verified for the external-pharmacy prescription workflow to ensure an authenticated pharmacy cannot access or modify prescription data outside its authorized scope.

18. Spoofing of Source Data Store OpenEMR Patient and Prescription DB  [State: Needs Investigation]  [Priority: High] 

Category:Spoofing
Description:OpenEMR Patient and Prescription DB may be spoofed by an attacker and this may lead to incorrect data delivered to OpenEMR Prescription Processing Service. Consider using a standard authentication mechanism to identify the source data store.
Justification:The Prescription Processing Service should accept data only from the authorized OpenEMR database using authenticated and restricted database connections. Deployment controls require verification.

Interaction: Prescription Record Read/Write

19. Spoofing of Destination Data Store OpenEMR Patient and Prescription DB  [State: Needs Investigation]  [Priority: High] 

Category:Spoofing
Description:OpenEMR Patient and Prescription DB may be spoofed by an attacker and this may lead to data being written to the attacker's target instead of OpenEMR Patient and Prescription DB. Consider using a standard authentication mechanism to identify the destination data store.
Justification:Database connections should be authenticated and restricted to authorized OpenEMR components. The exact database authentication and network restrictions are deployment-specific and require verification.

20. Potential SQL Injection Vulnerability for OpenEMR Patient and Prescription DB  [State: Mitigation Implemented]  [Priority: High] 

Category:Tampering
Description:SQL injection is an attack in which malicious code is inserted into strings that are later passed to an instance of SQL Server for parsing and execution. Any procedure that constructs SQL statements should be reviewed for injection vulnerabilities because SQL Server will execute all syntactically valid queries that it receives. Even parameterized data can be manipulated by a skilled and determined attacker.
Justification:OpenEMR secure coding guidance requires parameterized queries and bound parameters for database operations involving untrusted input, reducing SQL injection risk.

21. Potential Excessive Resource Consumption for OpenEMR Prescription Processing Service or OpenEMR Patient and Prescription DB  [State: Needs Investigation]  [Priority: High] 

Category:Denial Of Service
Description:Does OpenEMR Prescription Processing Service or OpenEMR Patient and Prescription DB take explicit steps to control resource consumption? Resource consumption attacks can be hard to deal with, and there are times that it makes sense to let the OS do the job. Be careful that your resource requests don't deadlock, and that they do timeout.
Justification:Excessive prescription requests could consume database connections or processing resources. Rate limiting, query timeouts, connection limits, and monitoring should be verified.
